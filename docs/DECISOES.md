# Decisões e divergências

Registro de decisões tomadas durante o desenvolvimento que divergem ou complementam `ESPECIFICACAO.md`. Uma entrada por decisão, mais recente no topo.

| Data | Área | Decisão | Motivo | Impacto no TG |
| --- | --- | --- | --- | --- |
| 2026-09-13 | Frontend (Fase 2) | Favoritos ("faculdades salvas") e pesquisas salvas são exclusivos do perfil Aluno (`A`), como já define a seção 2 da especificação ("Aluno: ... salvar faculdades, salvar pesquisas") | O protótipo (grupo-perfil.html) mostra essas telas dentro do perfil sem repetir essa restrição visualmente; registrando aqui para não ser lido como "qualquer usuário logado" ao implementar RF (Fase 4). Universidade (`U`) e Administrador (`D`) não têm essas telas | Nenhum: só explicita o que a seção 2 já diz |
| 2026-09-13 | Frontend (Fase 2) | Os exemplos de notificação do protótipo (GJNotificationBell no Design System Deck e nas pranchas) são ilustrativos; a lista real de tipos é a da seção 4.3: `NOVA_SUGESTAO`, `UNIVERSIDADE_PENDENTE`, `UNIVERSIDADE_APROVADA`, `SUGESTAO_AVALIADA` | O protótipo usa textos livres ("Sua universidade foi aprovada", "Nova sugestão recebida"...) para compor a tela visualmente; nem todo texto do protótipo corresponde 1:1 a um `tipo` do enum implementado no backend (RF16, Fase 4) | Nenhum: RF16 já define os 4 tipos: a UI é que não deve copiar literalmente os textos do protótipo como se fossem os únicos tipos possíveis |
| 2026-09-13 | Frontend (Fase 2) | T03a (avaliar) e o ícone de favorito (bookmark) em `DetalheUniversidadePage` são só a interface: não persistem nada | `POST /universidades/:id/avaliacoes` (RF02) e `/favoritos/universidades` são Fase 4; além disso, favoritos exigem perfil `A` autenticado, e a Fase 1 do frontend (login, sessão) ainda não foi construída. O botão "Avaliar" mostra o modal e a estrela funciona, mas "Enviar" só fecha com um aviso; o bookmark alterna um estado local (`setState`), sem chamada de API | Nenhum: UI pronta para ligar na Fase 4 |
| 2026-09-13 | Backend (Fase 2) | `GET /programas` e `GET /programas/:id` só retornam programas institucionais (`id_universidade` preenchido) cuja universidade tenha `status=A`; programas globais (`id_universidade` nulo) sempre aparecem | A seção 5.6 não detalha essa regra, mas a seção 6 (regra 1) já estabelece que "só `A` é listada publicamente"; deixar uma bolsa institucional pública antes da universidade ser aprovada vazaria a existência de uma instituição ainda não aprovada | Nenhum: extensão direta da regra de aprovação já prevista para universidades |
| 2026-09-13 | Backend (Fase 2) | `GET /universidades/:id/avaliacoes` foi implementado e retorna lista vazia até a Fase 4 (RF02) criar avaliações; mostra só o primeiro nome do autor (RNF17/RNF24) | A seção 11 já provisiona o endpoint GET nesta fase; a tabela `avaliacao` existe desde a Fase 0. Implementar o GET agora evita retrabalho e permite testar a paginação e a regra de privacidade mesmo sem o POST (que é RF02, Fase 4) | Nenhum |
| 2026-09-13 | Testes (Fase 2) | Além dos testes com Prisma mockado, os 4 módulos novos (universidades, campus, cursos, programas) foram validados de ponta a ponta contra um MySQL 8 real (mesmo procedimento das Fases 0/1: `mysqld` isolado, `db:local`, chamadas HTTP reais), incluindo a escrita em `visita_pagina` | As queries desses módulos usam `include`/`where` aninhados mais complexos (campus→endereço, curso→campus→endereço, programa→universidade); mocks não pegariam um nome de relação errado ou uma cláusula `where` inválida para o MySQL | Nenhum: reforça a confiabilidade sem mudar o contrato |
| 2026-09-11 | Banco de dados (bugfix bloqueante de CI) | Todas as colunas `DateTime` do schema Prisma passaram a usar `@db.DateTime(3)` explícito (em vez de `@db.DateTime` sem precisão); as duas migrations da Fase 0/1 foram consolidadas em uma única migration inicial | O job de CI falhava em todo push no passo `prisma migrate deploy` com `ERROR 1067 (42000): Invalid default value for 'criado_em'`. Causa raiz: `@db.DateTime` sem precisão gera coluna `DATETIME` (precisão 0), mas `@default(now())`/`@updatedAt` sempre geram `DEFAULT CURRENT_TIMESTAMP(3)` (precisão 3); MySQL 8 em modo estrito (`STRICT_TRANS_TABLES`, padrão da imagem `mysql:8.0`) rejeita esse descompasso de precisão. Corrigido igualando a precisão da coluna à do default. Consolidação da migration se justifica porque o banco nunca foi criado com sucesso em nenhum ambiente (todo `migrate deploy` falhava) | Sugere-se que o DDL do TG explicite `DATETIME(3)` em todas as colunas com `DEFAULT CURRENT_TIMESTAMP`, para evitar esse mesmo erro em outras implementações |
| 2026-09-11 | Escopo (Fase 1) | `POST /auth/register/universidade` (seção 5.1) não foi implementado nesta fase, mesmo estando na tabela de endpoints de Auth | A seção 11 (plano de fases) reserva explicitamente o cadastro de universidade para a Fase 3, junto com campus/cursos/programas, que ainda não existem como módulos. Implementá-lo agora pularia fase (regra do CLAUDE.md) | Nenhum: mantém a ordem de fases já definida na seção 11 |
| 2026-09-11 | Banco de dados (Fase 1) | `universidade.id_usuario` deixou de ser `NOT NULL` e passou a `ON DELETE SET NULL` | RNF17 exige exclusão física do usuário; a regra de negócio da seção 5.2 diz que, ao excluir um usuário tipo `U`, "a universidade vai para status=I" (ou seja, o registro da universidade permanece). Com `id_usuario NOT NULL` e sem ação de delete, a FK bloquearia essa exclusão (`RESTRICT`). Tornar a coluna anulável com `SET NULL` permite excluir o usuário e manter a universidade inativada | Sugere-se atualizar o DDL do TG: `UNIVERSIDADE.idUsuario` deveria ser opcional |
| 2026-09-11 | Backend (RF11) | `POST /usuarios` e `PATCH /usuarios/:id` não aceitam `tipoUsuario = 'U'` | Um usuário tipo `U` só faz sentido vinculado a uma universidade (`universidade.id_usuario`), criada apenas pelo fluxo de `/auth/register/universidade` (Fase 3). Permitir criar/converter para `U` por esses endpoints deixaria um usuário `U` órfão, sem universidade | Nenhum: RF11 não detalha esse caso; ficará documentado até a Fase 3 existir |
| 2026-09-11 | Testes (Fase 1) | Os testes de integração de `auth` e `usuarios` mockam o Prisma Client em vez de rodar contra um MySQL real | Não há Docker nem credenciais de um MySQL local disponíveis no ambiente onde o backend foi desenvolvido (ver pendência abaixo). Os testes cobrem rotas, validação (Zod) e regras de negócio; o schema/migrations continuam validados à parte pelo CI, que roda `prisma migrate deploy` contra um MySQL 8 real | Nenhum: é uma decisão de ambiente de desenvolvimento, não altera o contrato da API |
| 2026-09-10 | Backend (hash de senha) | Usar o pacote `bcryptjs` em vez de `bcrypt` (RNF02) | `bcrypt` é um binário nativo (node-gyp) e falha ao instalar em ambientes sem toolchain de compilação C++; `bcryptjs` é uma implementação pura em JavaScript, mesmo algoritmo e API compatível (`hash`/`compare`), sem dependência nativa | Nenhum: RNF02 exige o algoritmo bcrypt com custo configurável, não um pacote específico |
| 2026-09-10 | Banco de dados (migration inicial) | Ações referenciais (`ON DELETE` / `ON UPDATE`) de algumas FKs seguem o padrão do Prisma em vez do DDL literal da seção 4.3: `log_auditoria.id_usuario` usa `ON DELETE SET NULL` (o DDL não define ação, o que resultaria em `RESTRICT` e bloquearia a exclusão física de usuário com log); todas as FKs receberam `ON UPDATE CASCADE` | O DDL de referência não define `ON DELETE`/`ON UPDATE` explícitos para diversas FKs. O padrão do Prisma para FKs opcionais é `SET NULL`, o que é compatível com a regra de exclusão física de usuário (RNF17) sem quebrar a auditoria | Sugere-se registrar `ON DELETE SET NULL` explicitamente na FK de `log_auditoria.id_usuario` no DDL do TG |
